# 이음이 시맨틱 FAQ 캐시 설계

> "자주 묻는 질문은 저장된 답을 재사용해 공짜로 답한다" — 이 비용 구조를 이음이에
> 실제로 구현하기 위한 설계. 작성: 2026-10-03 · 갱신: 2026-10-05

---

## 1. 정의 (한 줄)
**시맨틱 캐시** = 어르신 질문을 <글자가 아니라 의미>로 저장된 FAQ와 비교하여, 비슷하면
**LLM을 쓰지 않고 저장된 답을 바로 돌려주는** 구조. 변동 없는 자주 묻는 질문에만 적용한다.

---

## 2. 왜 필요한가 (문제)
- 현재 이음이는 **매 질문마다 LLM이 새로 답**한다 → 질문당 약 31원, 통화당 약 260원
- 복지관 실운영(하루 수십 명)이면 월 수십만 원 → **무제한 무료 제공이 어려움**
- 목표 비용 구조: **"자주 묻는 질의응답은 저장답 재사용 = 거의 공짜"**

## 3. 지금 무엇이 빠져 있나
이음이에는 두 층 중 **①만 있고 ②가 없다.**

| 층 | 역할 | 이음이 현재 |
|---|---|---|
| ① 데이터 슬라이스 + RAG | 질문과 관련된 자료만 꺼내 LLM에 넘김 | ✅ 있음 (`retrieval.js`) |
| ② **시맨틱 FAQ 캐시** | 비슷한 질문은 저장답 재사용(LLM 생략) | ❌ **없음** |

→ ②가 없어서 **모든 질문이 매번 LLM 비용**을 낸다. 이 문서가 ②의 설계다.
(③ 프롬프트 캐싱은 "고정 지시문 90% 할인"일 뿐, 질문의 의미를 비교하지 않는다. 시맨틱 캐시와 다르다.)

## 4. 구조 (요청 처리 흐름)
```
어르신 질문
   │
   ├─[1] 변동 주제 판별
   │     날씨·오늘 열린 일자리·지역·어르신 개인정보 → 캐시 건너뜀(항상 LLM)
   │
   ├─[2] 질문을 "의미 벡터"로 변환 (임베딩)
   │
   ├─[3] FAQ 저장소에서 의미가 가장 가까운 항목 검색 (센터별로 분리)
   │        │
   │        ├─ 유사도 ≥ 임계값  → 저장된 검증답 바로 반환 ✅ (LLM 스킵 = 거의 공짜, ~0.1초)
   │        │
   │        └─ 임계값 미달      → RAG + LLM 생성(기존 방식, 비용)
   │                              + 이 질문·답을 FAQ 후보로 로깅
```

## 5. FAQ 저장소는 어떻게 채우나 (QA 고도화와 연결)
**QA 고도화로 쌓이는 검증답이 그대로 FAQ의 재료다.**
```
QA 질문뱅크(140+) → 자동 테스트 → 평가(충실/부족/틀림)
                                      ↓
                 "충실"로 검증된 질문·답을 FAQ 저장소에 등록(담당자 승인)
```
- 소스: `db/qbank.json` + `qa-eval-result.csv`의 충실 답변
- 담당자가 대시보드에서 **"이 답을 FAQ로 승인"** → 저장소 등록
- **변동 없는 주제만** 등록 (6번 참조)

## 6. 변동/비변동 구분 (안전의 핵심)
| 캐시 OK (변동 없음) | 캐시 금지 (변동 있음) |
|---|---|
| "보이스피싱이 뭐예요?" (상식) | "오늘 날씨?" (실시간) |
| "치매 검사 어디서?" (고정 안내) | "지금 열린 일자리?" (매일 바뀜) |
| "요양보호사 신청법?" (제도) | "내 이름/우리 동네 관련" (개인·지역) |
| "경로우대 혜택?" (전국 공통) | "이번 달 행사 일정?" (수시 변경) |

- 각 FAQ에 `volatile`(변동) 플래그 → 변동이면 애초에 캐시 안 함

## 7. 갱신 전략 — 변동성 분리 + 변경 감지 (★ 운영 핵심)
> 답변을 변동성으로 나누고, **변경된 것만 갱신**하면 구조가 단순해진다.
> "실시간 정합성"을 복잡하게 맞추지 않고, 변동은 아예 캐시하지 않으며 비변동만 캐시+갱신한다.

### 7-1. 변동성 분리 (1차 분기)
- **비변동** (상식·제도·고정 안내) → 캐시 대상
- **변동** (날씨·실시간 일자리·개인/지역) → 캐시 안 함, 항상 LLM

### 7-2. 갱신은 2중으로
```
[A] 변경 감지 — 즉시·자동 (핵심)
    서비스 자료를 재학습(sync)하면 → 그 서비스에 연결된 FAQ만 캐시 무효화
    → 다음 질문 때 새 답을 생성하고 다시 캐시
    예: 느티나무 공지 sync → 느티나무 관련 FAQ만 갱신 (나머지는 그대로 유지)

[B] 월 1회 전체 재검증 — 안전망
    변경 감지가 놓친 제도·금액 변경을 월 단위로 전체 점검·재검증
```
→ **[A]가 "업데이트된 것만 재분류"의 실제 구현**이다. 변경된 서비스의 FAQ만 똑똑하게 갱신하므로 효율적이고, [B]가 빠진 것을 잡아주는 안전망이다.

### 7-3. 단순해진 전체 그림
```
질문
 ├─ [변동 주제?] ──── 예 ──→ 항상 LLM (캐시 안 씀)
 │
 └─ 아니오 → [FAQ 캐시 조회(센터별)]
              ├─ 히트 → 저장답 (공짜·빠름)
              └─ 미스 → LLM 생성 + 캐시 저장

[갱신] sync로 서비스 변경 → 해당 FAQ만 무효화(자동) + 월 1회 전체 재검증
```

## 8. 구현 단계 — 단계적 접근 (측정 기반, 과공사 방지)
> **처음부터 임베딩을 넣지 않는다.** 먼저 단순 캐시로 "어르신이 실제로 얼마나 반복 질문하는지"(히트율)를
> 재고, 높을 때만 시맨틱을 올린다. 결정에 실제 숫자를 둔다.

### Phase A — 단순 캐시 (저비용·빠름·새 의존성 없음) ★먼저  ✅ **구현 완료 (2026-10-05)**
- 질문을 **정규화**(공백·문장부호 제거, NFC, 소문자화)하여 **완전/거의 일치** 매칭
  (조사 제거는 뜻을 바꿀 수 있어 보수적으로 보류 — 히트율 보고 다음에 조정)
- 필수: **center 키 분리**(center_id) + **변동 주제 제외**(6·7번) + prompt_hash(프롬프트 바뀌면 자동 무효화) + TTL
- 목적: **히트율 측정** — 임베딩 없이도 "같은/비슷한 질문 반복 비율"을 실데이터로 확보
- 장점: 임베딩 비용 0, 추적 쉬움(왜 매칭됐는지 글자로 설명 가능)

**구현 파일 (ieumi-server):**
- `db/migrations/011_qa_cache.sql` — `qa_cache`(답 저장) + `qa_cache_event`(히트율 로그). pgvector 없음(Phase A).
- `qa-cache.js` — 정규화·promptHash·변동감지·조회·저장·이벤트로그. 원본(ask-core)의 단순 Node 포팅.
- `server.js` `/chat` — 답변 생성 앞뒤에 조회/적재 끼움. 어떤 오류도 대화를 막지 않음(best-effort).
- `db/qa-cache-stats.js` — 히트율·우회사유·자주 묻는 질문 측정(크레딧 0).

**운영 (env `QA_CACHE_MODE`):** `off`(기본, 동작 영향 0) → `shadow`(조회·기록만, 답은 늘 LLM) → `on`(히트 시 캐시 답).
- **반드시 shadow 먼저** 며칠 돌려 히트율·오매칭 확인 후에만 `on` 전환 (설계 11번 ③, 그림자 모드).
- shadow 는 임베딩·추가 LLM 이 없어 **크레딧을 더 쓰지 않음** — 라이브에서 안전하게 측정 가능.
- 측정: `node db/qa-cache-stats.js` → 히트율이 의미 있게 높으면 Phase B 투자, 낮으면 다른 절감 우선.

### Phase B — 시맨틱 매칭 (Phase A 히트율이 높을 때만)
- Phase A에서 **히트율이 의미 있게 나오면** → 임베딩+유사도 매칭을 그 위에 추가
- 근거: 실제 히트율 숫자로 **ROI 확인 후** 투자 (기존 구현 재사용, 9번)

### 공통 구현 작업 (Phase A/B 걸쳐)
| 작업 | 내용 | 비고 |
|---|---|---|
| FAQ 저장소 테이블 | 질문(정규화형)·검증답·주제·volatile·center·출처·검증일 (+Phase B: 임베딩 열) | DB |
| 변동 주제 라우팅 | 서버 `/chat` 앞단에 캐시 조회 | server.js |
| 갱신 로직 | sync 시 해당 FAQ 무효화 + 월 1회 재검증 | 7번 전략 |
| 대시보드 FAQ 승인 | 담당자가 충실답 → FAQ 등록 | QA 대시보드 연계 |
| 히트율/정확도 로깅 | 캐시 히트·미스·오매칭 기록 | 측정·추적 |

## 9. 기술 선택지

### ★ 최우선 — 기존 구현 재사용
사내 다른 프로젝트(`ask-core` = ai-avatar-core)에 **시맨틱 캐시가 이미 완전히 구현되어 있다.** 새로 만들기보다 이식을 최우선으로 검토한다.
- `src/migrations/...CreateAvatarChatSemanticCache.ts` — 캐시 테이블
- `src/migrations/...AddAudioObjectNameToSemanticCache.ts` — **답변 음성까지 캐시** (음성 키오스크 이음이에 최적)
- `src/migrations/...AddSemanticCacheBillingAndChatTurnCacheRef.ts` — 과금 집계 + 캐시 참조
- `src/migrations/...CreateAvatarEmbeddingUsage.ts` — 임베딩 사용량
- `src/modules/topic/topic-match.service.ts` — 주제 매칭(변동/비변동 분류에 활용 가능)
- `src/modules/realtime/realtime-orchestrator.service.ts` — 대화 흐름에서 캐시 조회
- `tools/semantic-cache-live-test.js` — 라이브 테스트 도구
- **재사용 가능 로직**: 임베딩·유사도 매칭·센터별 분리·과금 집계·음성 캐시
- **주의**: ask-core는 NestJS 구조, 이음이는 단순 Node 서버 → 로직 재사용 + 구조 포팅 필요(복붙 불가)

### 대안 (이식이 어려울 경우)
| 방식 | 장점 | 단점 |
|---|---|---|
| 임베딩 + pgvector | 의미 매칭 정확 | 새 의존성·임베딩 비용(극소) |
| 키워드+의미 하이브리드 (retrieval 확장 + 경량 LLM 확인) | 의존성 적음 | FAQ 많아지면 한계 |

## 10. 비용 효과
```
현재:   통화 8질문 × 31원 = 약 260원  (전부 LLM)
캐시 후: FAQ 히트 5개(≈0원) + LLM 3개(93원) = 약 100원
         → 통화 비용 260원 → 100원 (반복 질문 비율에 비례해 더 내려감)
```
- **반복되는 FAQ가 많을수록 효과 큼** / 질문이 매번 다르면 효과 작음
- FAQ 히트는 LLM을 아예 안 부르므로 거의 공짜(임베딩 조회 비용만)

## 11. 단점·우려와 안전장치 (검토 결과)
도입 시 반드시 다룰 3원칙과, 추가 우려·대응.

| 위험 | 설명 | 안전장치 |
|---|---|---|
| **① 센터별 분리 (필수)** | 멀티테넌트 → 한 복지관 답이 다른 복지관으로 샐 위험 | 캐시 키에 **center 포함** |
| **② 시간민감 답변 제외** | 날씨·마감되는 일자리·실시간을 캐시하면 어제 정보가 오늘 나감 | 변동 주제 **캐시 제외**(6·7번) |
| **③ 추적성** | 시맨틱 매칭은 "왜 이 답이 나왔나" 설명이 어렵다 (84세 어르신이 쓰는 서비스) | 매칭 근거 로깅 + **그림자 모드(기록만)→검증→적용** 점진 도입 |
| 오매칭 | "기초연금 얼마?"↔"어디서 신청?"처럼 비슷해도 답이 다름 | 유사도 **임계값 높게** + FAQ 담당자 검증 |
| 유지보수 | 제도·금액 변경 시 옛 답 고착 | 7번 **갱신 전략**(변경감지+월1회) |
| 미스 시 지연 | 임베딩+검색 오버헤드(히트 아닐 때) | 히트율 높으면 전체 평균은 오히려 빨라짐 |

- 효과 크기는 **실운영 로그(반복 질문 비율)** 로 검증해야 확정됨 (지금은 시연이라 데이터 부족)
- FAQ 답은 **담당자 검증을 거친 것만** (틀린 답을 캐시하면 틀린 답이 반복됨)
- 이음이는 **정확성이 최우선**인 어르신 서비스 → 위 안전장치를 갖춘 뒤 점진 도입

## 12. 두 층의 관계 (요약)
```
"데이터를 슬라이스하게 정리"   = ① RAG (이미 있음, retrieval.js)
"자주 묻는 질의응답은 공짜"     = ② 시맨틱 FAQ 캐시 (이 문서, 미구현 → 구축 대상)
두 개가 합쳐지면 = 목표한 비용 구조가 완성된다.
```

## 13. 역할 분담
- **백엔드 구현/이식**: 서버 개발 담당 (ask-core 로직 재사용 + 이음이 구조 포팅)
- **FAQ 재료·검증·QA**: 운영/기획 (QA 고도화로 검증답 축적, 담당자 FAQ 승인)
- **갱신 운영**: 변경 감지는 자동(sync 연동), 월 1회 재검증은 담당자 점검
