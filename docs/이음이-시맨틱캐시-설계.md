# 이음이 시맨틱 FAQ 캐시 설계

> "자주 묻는 질문은 저장된 답을 재사용해 공짜로 답한다" — 탐 팀이 처음 구상한 비용 구조를
> 이음이에 실제로 구현하기 위한 설계. 작성: 2026-10-03

---

## 1. 정의 (한 줄)
**시맨틱 캐시** = 어르신 질문을 <글자가 아니라 의미>로 저장된 FAQ와 비교하여, 비슷하면
**LLM을 쓰지 않고 저장된 답을 바로 돌려주는** 구조. 변동 없는 자주 묻는 질문에만 적용한다.

---

## 2. 왜 필요한가 (문제)
- 현재 이음이는 **매 질문마다 Claude(LLM)가 새로 답**한다 → 질문당 ~31원, 통화당 ~260원
- 복지관 실운영(하루 수십 명)이면 월 수십만 원 → **무제한 무료 제공이 어려움**
- 탐 팀 원래 사업 논리(일꾼을묻다): **"자주 묻는 질의응답은 저장답 재사용 = 공짜"**

## 3. 지금 무엇이 빠져 있나
이음이에는 두 층 중 **①만 있고 ②가 없다.**

| 층 | 역할 | 이음이 현재 |
|---|---|---|
| ① 데이터 슬라이스 + RAG | 질문과 관련된 자료만 꺼내 LLM에 넘김 | ✅ 있음 (`retrieval.js`) |
| ② **시맨틱 FAQ 캐시** | 비슷한 질문은 저장답 재사용(LLM 생략) | ❌ **없음** |

→ ②가 없어서 **모든 질문이 매번 LLM 비용**을 낸다. 이 문서가 ②의 설계다.

## 4. 구조 (요청 처리 흐름)
```
어르신 질문
   │
   ├─[1] 변동 주제 판별
   │     날씨·오늘 열린 일자리·지역·어르신 개인정보 → 캐시 건너뜀(항상 LLM)
   │
   ├─[2] 질문을 "의미 벡터"로 변환 (임베딩)
   │
   ├─[3] FAQ 저장소에서 의미가 가장 가까운 항목 검색
   │        │
   │        ├─ 유사도 ≥ 임계값  → 저장된 검증답 바로 반환 ✅ (LLM 스킵 = 거의 공짜, ~0.1초)
   │        │
   │        └─ 임계값 미달      → RAG + LLM 생성(기존 방식, 비용)
   │                              + 이 질문·답을 FAQ 후보로 로깅
```

## 5. FAQ 저장소는 어떻게 채우나 (QA 고도화와 연결)
**지금 하는 QA 고도화가 그대로 FAQ의 재료다.**
```
QA 질문뱅크(140+) → 자동 테스트 → Haiku 평가(충실 97%)
                                      ↓
                 "충실"로 검증된 질문·답을 FAQ 저장소에 등록(담당자 승인)
```
- 소스: `db/qbank.json` + `qa-eval-result.csv`의 충실 답변
- 담당자가 대시보드에서 **"이 답을 FAQ로 승인"** → 저장소 등록
- **변동 없는 주제만** 등록 (아래 6번)

## 6. 무엇을 캐시하고 무엇을 하지 않나 (안전의 핵심)
| 캐시 OK (변동 없음) | 캐시 금지 (변동 있음) |
|---|---|
| "보이스피싱이 뭐예요?" (상식) | "오늘 날씨?" (실시간) |
| "치매 검사 어디서?" (고정 안내) | "지금 열린 일자리?" (매일 바뀜) |
| "요양보호사 신청법?" (제도) | "내 이름/우리 동네 관련" (개인·지역) |
| "경로우대 혜택?" (전국 공통) | "이번 달 행사 일정?" (수시 변경) |

- 각 FAQ에 `volatile`(변동) 플래그 → 변동이면 애초에 캐시 안 함
- 제도·금액이 바뀌면 해당 FAQ **만료/갱신** (주기 점검)

## 7. 구현 단계
| Phase | 내용 | 비고 |
|---|---|---|
| 1 | **FAQ 저장소 테이블** (질문·검증답·임베딩·주제·volatile·출처·검증일) | DB 마이그레이션 |
| 2 | **질문 임베딩 + 유사도 검색** | pgvector(Neon 지원) 또는 경량 하이브리드 |
| 3 | **변동 주제 라우팅** (서버 `/chat` 앞단에 캐시 조회) | server.js |
| 4 | **대시보드에서 FAQ 승인** (담당자가 충실답 → FAQ 등록) | QA 대시보드 연계 |
| 5 | **실운영 로그로 FAQ 확장** (반복 질문 자동 후보화) | 운영 축적 |

## 8. 기술 선택지 (Phase 2)
| 방식 | 장점 | 단점 |
|---|---|---|
| **임베딩 + pgvector** (Voyage/OpenAI 임베딩) | 의미 매칭 정확, 확장성 | 새 의존성·임베딩 비용(극소) |
| **키워드+의미 하이브리드** (기존 retrieval 확장 + Haiku 확인) | 의존성 적음, FAQ 적을 때 충분 | FAQ 많아지면 한계 |

→ **초기(FAQ 수십~수백)는 하이브리드로 시작**, FAQ가 많아지면 임베딩+pgvector로 전환 권장.

## 9. 비용 효과 (탐 팀 논리의 실현)
```
현재:   통화 8질문 × 31원 = 약 260원  (전부 LLM)
캐시 후: FAQ 히트 5개(≈0원) + LLM 3개(93원) = 약 100원
         → 통화 비용 260원 → 100원 (반복 질문 비율에 비례해 더 내려감)
```
- **반복되는 FAQ가 많을수록 효과 큼** / 질문이 매번 다르면 효과 작음
- FAQ 히트는 **LLM을 아예 안 부르므로 거의 공짜**(임베딩 조회 비용만)

## 10. 전제·주의
- 효과 크기는 **실운영 로그(반복 질문 비율)** 로 검증해야 확정됨 (지금은 시연이라 데이터 부족)
- FAQ 답은 **담당자 검증**을 거친 것만 (틀린 답을 캐시하면 틀린 답이 반복됨)
- 변동 주제 분류가 생명 — 잘못 캐시하면 **어제 정보를 오늘 어르신께** 줄 수 있음
- 이음이는 라이브 프로덕션 → 캐시 도입은 **그림자 모드(기록만)→검증→실제 적용** 순으로 점진

## 11. 두 층의 관계 (요약)
```
"데이터를 슬라이스하게 정리"   = ① RAG (이미 있음, retrieval.js)
"자주 묻는 질의응답은 공짜"     = ② 시맨틱 FAQ 캐시 (이 문서, 미구현 → 구축 대상)
두 개가 합쳐지면 = 탐 팀이 처음 구상한 비용 구조가 완성된다.
```
